# Data format (v2)

Both the Python and Node packages load data that is **generated by the pipeline**
from the canonical `data/build/pincodes.normalized.jsonl.gz`
(`python -m pipeline.build --emit-packages`). Nothing here is hand-authored.

There are two packages, each with its own data:

- **core** (`indian-pincode` / `@devzoy/indian-pincode`): validation + pincode →
  state/district(s). Small, no coordinates.
- **geo** (`indian-pincode-geo` / `@devzoy/indian-pincode-geo`): post offices,
  coordinates, nearby search, reverse lookup. Larger, depends on core.

---

## Core format

### Design goals

- Handle pincodes that belong to **multiple districts** (1,478 of ~19,600 do).
- **No Node built-ins** in the JS core (no `fs`/`path`), so it works unchanged in
  browsers, bundlers (Vite/webpack/esbuild), edge runtimes, and React Native. Data is
  imported as a module.
- **Python** loads via `importlib.resources`.
- **Synchronous** and **memoized**; cold load target < 50 ms.
- Small: budget ≤ 500 KB unpacked (target ≤ 300 KB).

### Chosen encoding: string tables + delta-encoded parallel arrays

The core payload is a single JSON object (`core-data.json`), shipped as a data module.
It has these fields:

| field | type | meaning |
| :--- | :--- | :--- |
| `version` | string | `data_version` (e.g. `2025.10.03`) |
| `states` | `string[]` | state/UT names; index = state id |
| `districts` | `string[]` | district names (UPPERCASE); index = district id |
| `pincodes` | `int[]` | **delta-encoded** sorted pincodes (see below) |
| `stateIdx` | `int[]` | parallel to `pincodes`; state id, or `-1` if unknown |
| `districtGroups` | `(int \| int[])[]` | parallel to `pincodes`; a district id, or an array of district ids for multi-district pincodes |

**Delta encoding.** Pincodes are sorted ascending and stored as successive
differences: `pincodes[0]` is the first pincode; each later entry is
`pin[i] - pin[i-1]`. Deltas are small positive integers, which keeps the JSON compact
and lets a bundler/minifier compress well. Decoding is a single cumulative sum at load.

**Lookup.** To resolve a pincode:
1. Binary-search the reconstructed sorted pincode array for the integer value.
2. If found at index `i`, the state is `states[stateIdx[i]]` (or `null` if `-1`) and the
   districts are `districts[d]` for each id in `districtGroups[i]`.

`validate(pin)` is a binary-search membership test (true only if the pincode exists —
not merely a 6-digit format check). `isWellFormed(pin)` does the format-only check
(`^[1-9][0-9]{5}$`).

Everything is loaded once and memoized. The JS core decodes the module lazily on first
call; Python reads the JSON via `importlib.resources` on first call.

### Why not a bitset?

A 900,000-bit validity bitset (~112 KB) was considered. It answers `validate` cheaply
but still needs a separate structure for pincode → state/district(s), which is the bulk
of the payload anyway. The sorted delta array doubles as the validity set and the key
space for the state/district maps, so a single structure serves both. With gzip/bundler
compression the delta array is comparable in size to a bitset while also carrying the
mappings.

## Geo format

### Node geo

- **Coordinates** are stored as **int32 at 1e-5 degree precision**
  (`round(value * 1e5)`), which resolves to ~1 m and fits every Indian coordinate in a
  signed 32-bit int. This halves the storage vs float64 and is exact enough for postal
  points.
- **Records**: one row per post office with
  `pincode, officeName, officeType, deliveryStatus, district, state, lat(int32),
  lon(int32), geoQuality`. Stored as compact JSON shards loaded lazily with `fs`
  (Node-only; browser geo is out of scope — stated in the geo README).
- **Spatial index**: a **0.1° grid**. Each grid cell key is `"{latCell},{lonCell}"`
  where `latCell = floor(lat / 0.1)`. The index maps each cell to the list of record
  offsets whose coordinates fall in it. `findNearby` computes the set of cells
  overlapping the search circle (radius converted to a cell span), scans only those
  cells, filters by haversine distance, then sorts. No full scan.
- **Centroids**: `pincode → {lat, lon}` (int32), computed from non-suspect coordinates,
  used by `getCentroid` and `reverseLookup`. `reverseLookup` uses the same grid over the
  centroid set.

`geoQuality = "suspect"` records are **excluded from `findNearby`/`reverseLookup` by
default** and included only when `includeSuspect: true` (JS) / `include_suspect=True`
(Python).

### Python geo

- A compact **SQLite** database (`geo.sqlite`) with a `post_offices` table indexed on
  `(lat, lon)` and on `pincode`. `find_nearby` uses a **bounding-box prefilter**
  (`lat BETWEEN ... AND lon BETWEEN ...`) followed by a haversine filter and sort. It
  does **not** depend on the SQLite R*Tree module being available.
- A `centroids` table for `get_centroid`/`reverse_lookup`.
- Coordinates are stored as REAL (SQLite has no int32 gain); the file is kept compact by
  storing only the fields needed and relying on SQLite page compression of repeated
  strings via a `states`/`districts` lookup is unnecessary at this size.

## Generation

`python -m pipeline.build --emit-packages` reads `pincodes.normalized.jsonl.gz` and
writes, for each package, the data files into the package source tree:

- core (Node): `src/node/core/data/core-data.json`
- core (Python): `src/python/indian_pincode/data/core-data.json`
- geo (Node): `src/node-geo/data/records.json`, `grid.json`, `centroids.json`
- geo (Python): `src/python-geo/indian_pincode_geo/data/geo.sqlite`

The emitters are deterministic: same canonical input → byte-identical package data.
